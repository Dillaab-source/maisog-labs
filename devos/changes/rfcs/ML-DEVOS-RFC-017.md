# ML-DEVOS-RFC-017: S5 Capability & Permission Gateway

Status: `IMPLEMENTED AND CLOSED — ML-DEVOS-ADR-015 / D-065`

Proposed change class: `ARCHITECTURE`

Sentinel phase:
- `S5 — Capability & Permission Gateway`

Authority chain: `D-058` (Paulo) authorizes this proposal/audit step only, following S4's closure at Sentinel `v1.7.0` (`ML-DEVOS-ADR-014`, `D-051`, `ML-DEVOS-AS-068`) and the completion of the WEB-REL-001 release-baseline gates. This RFC is itself the Architect Sync input for S5; it grants no authority and authorizes no implementation. Per `D-058` and `coordination/ARCHITECT_REVIEW.md`'s Builder Brief for this cycle, no executable S5 gateway or permission-enforcement code is created by this RFC — every artifact named below is a planned deliverable of a future, separately authorized S5 implementation cycle.

## Problem

`ML-DEVOS-ARCH-001` §4–§5 names a **Capability Registry / Gateway** as a frozen system mechanism — "determines what CAN technically be done, as distinct from Governance, which determines what MAY be done" — and `devos/capabilities/` has stood reserved for it since S2 (`ML-DEVOS-RFC-001`, `ML-DEVOS-AS-006`, `D-016`), currently `NOT_IMPLEMENTED`. `CORE-002` ("Capability != Authority") and `CORE-008` ("installed capability does not grant authority") are both already active, constitutional-and-capability-class rules — but nothing in this repository today technically enforces either. Whether a given actor's request to invoke a given tool against a given resource is even *technically permitted* is decided by nothing more than informal prose review at authorization time; there is no deterministic, fail-closed decision function anyone or anything actually calls.

S3 Typed Task Contracts (`ML-DEVOS-RFC-013`) built the typed *description* of what a task is authorized to do, explicitly excluding permission enforcement ("no capability/tool/credential enforcement... that is S5"). S4's State Machine Kernel (`ML-DEVOS-RFC-016`) built the authoritative *lifecycle* record, explicitly stating the same boundary ("the kernel accepts a bare `actor_id` string... and performs no general actor permission check... until S5 exists"). Both phases deliberately deferred the same open question: given an actor, a project, a tool/provider, an action, a resource scope, and an environment, is this specific invocation *technically* permitted right now — and if not, exactly why not?

Left unaddressed, Sentinel can describe what a task is authorized to do (S3) and track what stage it is in (S4), but has no deterministic mechanism that actually stands between an actor and a tool invocation to answer "can this technically happen" independently of whether it *should* happen.

## Motivation

As Sentinel's actor surface grows (Builder, QA, Architect, and a future Orchestrator dispatching work across providers — shell, GitHub, Cloudflare, MCP tools, browser/UI automation), informal review of "is this technically permitted" does not scale and does not fail closed: a misconfigured tool binding, a stale credential, an actor operating outside its intended project, or a request against an unrecognized resource scope can silently proceed with no structural backstop. `ML-DEVOS-ARCH-001` §4–§5 already names this as a frozen target mechanism; S5 is what turns that accepted intent into an actual, reviewable design, following the exact discovery → design → Architect Sync → Paulo-gated implementation sequence S3 and S4 already used.

If this RFC is not accepted, S5 remains unauthorized and every future capability decision continues to rely entirely on prose authorization and ordinary code review, with `CORE-002`/`CORE-008` remaining true in principle but technically unenforced.

## Proposed change

This RFC proposes the design only. Per `D-058`'s explicit authorization, **no executable implementation, schema file, or live policy/decision mechanism is created by this RFC** — every artifact named below is a planned deliverable of a future, separately authorized S5 implementation cycle, not a file this cycle writes.

### 1. Scope of the gateway — what S5 is and is not

The S5 Capability & Permission Gateway is proposed as **a pure, deterministic decision function over a request and a versioned policy document** — not a credential store, not a secrets manager, not a governance-authority decider, not an active enforcement daemon that intercepts traffic. Concretely, the gateway:

- **is**: a library exposing one primary operation, `evaluate(subjectContext, requestIntent, policy, revocationList, evaluationContext) -> decision`, plus policy-loading/versioning helpers, that answers exactly one question — *is this specific (actor, project, tool, action, resource scope, environment) combination technically permitted under the presented, pinned policy version, the current revocation list, and the trusted moment of evaluation* — and nothing else. The operation deliberately takes a **trusted** `subjectContext`, a **trusted** `evaluationContext` (§3, §11 — added to correct finding `AS76-F001`'s purity/clock contradiction), and an **untrusted** `requestIntent` as separate arguments, never one merged "request" object (§3, correcting the Architect's Stage Gate Review finding `AS75-F001` — not cited here by its full Architect Sync identifier ahead of its own durable archive existing, consistent with how every prior Architect Sync in this repository has been cited only after `devos/changes/architect-syncs/` records it). `evaluate()` itself is additionally not the public surface an untrusted caller invokes directly — §3 and §9 define the trusted adapter-wrapper boundary that alone can construct a valid `subjectContext`/`evaluationContext` (correcting finding `AS76-F002`).
- **is not**: a governance-authority decider. It never determines whether an action *should* happen, whether a human has approved it, or whether a task is in-scope per its Task Contract (S3) or in the right lifecycle state to attempt it (S4) — those remain entirely the callers' and Architect/Paulo's responsibility. An `ALLOW` decision from S5 answers only the CAN question; it never answers the MAY question (`ML-DEVOS-ARCH-001` §5).
- **is not** a credential broker or secrets manager. It evaluates *credential requirement descriptors* (does this action require a credential of a named class, and is one declared to exist for this actor/environment) — it never stores, issues, rotates, or exposes an actual secret value (§6 below).
- **is not** an active enforcement daemon. It does not intercept, wrap, or proxy real tool calls; a future integration point (a provider adapter, an Orchestrator, or a tool-invocation wrapper) would call `evaluate()` before acting and respect its decision — S5 itself never runs as a service sitting in the traffic path.

This distinction bounds S5 sharply against S6 (isolated execution), S7 (evidence storage/QA), S8 (orchestration/dispatch), and S9 (Evidence Gate sufficiency judgment), mirroring exactly the boundary discipline `ML-DEVOS-RFC-016` §A and §H already established for S4.

### 2. Capability descriptors (provider-neutral)

A **capability descriptor** is the static, policy-authored unit the gateway evaluates a request against. Each descriptor is provider-neutral — it never embeds a provider-specific authority concept (e.g. a GitHub permission string or a Cloudflare API scope) directly; a provider adapter (§9) translates between a provider's native vocabulary and this shape. A descriptor's required fields:

| Field | Shape | Meaning |
|---|---|---|
| `descriptor_id` | `^[A-Z][A-Z0-9_-]*$`, ≥3 chars | Stable identifier, reusing S4's exact task-id shape convention (`isValidTaskId()`) rather than inventing a second identifier grammar. |
| `actor_role` | one of the frozen `ML-DEVOS-ARCH-001` §3 actors (`Paulo`, `Architect`, `Builder`, `QA`, `Independent Reviewer`) or a named future role | Which actor role this descriptor applies to. Never a bare unauthenticated identity string — descriptors are role-scoped, not person-scoped, consistent with `CORE-008`'s "roles/projects/scopes" framing. |
| `project` | repository/project scope string (e.g. `Dillaab-source/maisog-labs`), or the literal `*` for a Sentinel-wide descriptor | Reuses S3's `project` field shape rather than inventing a second project-scope grammar. |
| `provider` | one of the bounded V1 adapter names (§9) — `shell`, `github`, `cloudflare`, `mcp`, `browser`, or a future registered value | Which capability subsystem (`ML-DEVOS-ARCH-001` §4's "Skills, MCP tools, GitHub, Cloudflare, n8n, shell, browser, and future APIs") this descriptor governs. |
| `action` | provider-scoped action name (e.g. `git.push`, `pr.merge`, `d1.migrate`, `shell.exec`) | The specific technical operation, named in the provider's own vocabulary via the adapter boundary — never a Sentinel-invented universal verb set that would have to keep pace with every provider's API surface. |
| `resource_scope` | non-empty array of bounded resource patterns, in the exact V1 grammar defined below | The exact resource(s) this descriptor covers. An empty array is a schema violation, not "everything" — unbounded scope must be spelled out explicitly (`resource_scope: ["*"]`), never implied by omission. |
| `environment` | one of `local`, `ci`, `staging`, `production`, or a future registered value | Mirrors the environment axis `CORE-019` already requires for remote-resource authorization records. |
| `expiry` | ISO-8601 timestamp, or `null` for a descriptor with no fixed expiry (still subject to `policy_version` pinning/revocation, §6, §11) | When this descriptor stops being valid. A `null` expiry is not "forever, unconditionally": once its containing policy version is superseded and no successor descriptor exists for the same key, the descriptor is **not grantable to new attempts after supersession**. Supersession does not retroactively invalidate an attempt already pinned to the older version (§6); the moment its `descriptor_id` appears in the live revocation list (§6), it is denied for every attempt, pinned or not. *(Wording reconciled per `ML-DEVOS-AS-077`'s non-blocking design note, as required by `D-063`.)* |
| `credential_requirement` | `{ required: boolean, credential_class: string \| null }` | Whether this action requires a credential, and if so, a named *class* (e.g. `github_pat_scoped`, `cloudflare_api_token`) — never a value, reference path, or hint at where a secret lives (§7). |
| `consequence_tier` | reuses the existing `core-rules.json` risk vocabulary exactly: `low` \| `medium` \| `high` \| `highest` | Deliberately the same four-value vocabulary already canonical for `CORE-*` rules, rather than inventing a second risk taxonomy S5 would have to keep synchronized with the first. This is a **policy-authoring classification only** (§8) — it is never itself an evaluation-time gate input (corrected per `AS75-F002`; see §8). |

A descriptor is a **policy artifact**, not a grant instance — per-request evaluation (§3) is what actually produces a decision for a specific attempt; the descriptor only says what a currently-pinned policy version considers technically expressible for a role/project/provider/action/resource/environment combination.

**`resource_scope` grammar and matching precedence (V1, bounded — corrects `AS75-F004`).** Each pattern in `resource_scope` is exactly one of three forms, no others permitted in V1:

1. **Exact literal** — a full resource string with no wildcard, matching only that identical, canonicalized resource value.
2. **Prefix wildcard** — a literal prefix followed by exactly one trailing `/*` (e.g. `refs/heads/release/*`), matching any canonicalized resource sharing that literal prefix. Exactly one trailing wildcard is permitted; an infix or multiple wildcard (`a/*/b`, `a/**`) is a schema violation, not a richer pattern.
3. **Bare `*`** — matches any canonicalized resource for the descriptor's already-matched `(actor_role, project, provider, action, environment)` tuple.

No regular expressions, character classes, or negation are part of the V1 grammar — a policy author needing more expressive matching must wait for a future governed schema extension, not encode it into a literal string this grammar cannot express.

**Canonicalization is a per-adapter contract, never a universal recipe (corrects `AS76-F003`).** The prior draft applied one generic recipe (Unicode NFC, one percent-decode pass, trailing-slash stripping) to every provider's resources alike — but shell paths, GitHub identifiers, Cloudflare/MCP opaque IDs, and browser URLs are not equivalent resource domains, and a generic decode step can itself change an opaque identifier's meaning. **The core matcher (§3) never canonicalizes anything itself** — it only ever compares values that are already canonical, using the exact-literal/prefix-wildcard/bare-`*` grammar above as a pure string-pattern comparison with no decoding step of its own. Canonicalization — defining what "the" canonical form of a given provider's resource even is, and rejecting a value that cannot be safely reduced to it — is entirely the responsibility of the originating provider adapter's own contract (§9), which each V1 adapter must specify individually. A `resource` value the adapter cannot safely canonicalize is `MALFORMED_REQUEST` (§4) at the adapter boundary, before it ever reaches the core matcher — never guessed, never partially normalized, and never decoded by the matcher itself.

**Matching precedence (deterministic, corrects `AS75-F004`'s nondeterminism).** For a given evaluation, every descriptor matching on `(actor_role, project, provider, action, environment)` is additionally scored on two axes: **project specificity** (an exact `project` match outranks a `project: "*"` descriptor) and **resource specificity** (an exact-literal match outranks a prefix-wildcard match; among prefix-wildcard matches, a longer literal prefix outranks a shorter one; a bare `*` match is lowest) — computed entirely over the already-canonical strings the adapter emitted, never over provider-native or partially-decoded forms. The descriptor with the strictly highest combined `(project specificity, resource specificity)` rank is selected. **If two or more descriptors tie at the highest combined rank — regardless of whether their `consequence_tier`/`credential_requirement` happen to agree — the decision is `DENY`/`AMBIGUOUS_POLICY_MATCH` (§4)**, correcting the prior, narrower rule that only denied on a *materially differing* tie.

### 3. Decision contracts

**The trusted adapter-wrapper boundary — corrects `AS76-F002`.** Cycle 1 moved role/credential assertions into a `subjectContext` argument and required its `attested_by` field to name a registered adapter, but left the actual construction of that object reachable by any caller who could write a matching object literal — a naming convention, not a mechanical boundary. V1 closes this by making `evaluate()` itself **not** the surface an untrusted caller ever invokes directly. Three layers, kept explicitly distinct:

1. **Untrusted external caller input** — the `requestIntent` (below) an arbitrary caller supplies to one of the bounded V1 adapters' own public entry points (e.g. `adapters.github.request(requestIntent)`). This is the only thing an external caller ever provides.
2. **Adapter/host-authenticated subject and evaluation facts** — computed *internally*, by the adapter's own wrapper code, from its own trusted execution environment (e.g. the identity carried by an already-authenticated CI job token, a webhook's provider-verified signature, or the process's own trusted clock) — **never from any field the caller passed in**. The wrapper, not the caller, constructs `subjectContext` and `evaluationContext` from these internally-derived facts.
3. **The internal pure evaluator input** — `evaluate()`'s five arguments. `subjectContext` and `evaluationContext` are typed as **opaque, branded values**: a plain object literal an arbitrary caller constructs by hand does not satisfy the brand, so `evaluate()` can mechanically distinguish "a value actually produced by a registered adapter wrapper's internal construction path" from "a value merely shaped like one." (No cryptographic attestation system is required for V1 — a module-private brand/token that only adapter-internal code can mint is sufficient, provided its trust assumptions and bypass limits are stated plainly, as they are here.)

**What `evaluate()` itself validates versus what the wrapper guarantees.** `evaluate()` validates that a presented `subjectContext`/`evaluationContext` carries a genuine brand from a registered adapter (structural/source validation, step (a) below) — it has no way to verify, and does not attempt to verify, that the *content* of that branded value is truthful. Truthfulness of content (that `actor_role`/`credential_available`/`evaluationContext.time` accurately reflect the real authenticated caller and the real current moment) is entirely the constructing adapter wrapper's guarantee, made only once, at construction time, from its own trusted environment. A compromised or buggy *registered* adapter remains a disclosed residual risk (§9, Threat model) — the brand boundary closes the *arbitrary-external-caller* forgery vector `AS75-F001`/`AS76-F002` identified; it does not and cannot make every registered adapter individually trustworthy.

**Subject context (trusted).** `subjectContext`'s fields: `actor_role`; `actor_id` (an opaque identity string, exactly as S4's `claim()`/`transition()` already accept a bare `actor_id` with no permission judgment attached to it); `credential_class` and `credential_available: boolean` (the same class-only, never-a-value attestation §7 already required); `attested_by` (the exact registered adapter/host name — one of §9's bounded provider names — whose wrapper constructed this branded value); and `attestation_ref` (an opaque correlation string for audit purposes, never a secret or credential value). `evaluate()` treats every field of `subjectContext` as already-attested fact; it never re-derives or second-guesses `actor_role`/`credential_available` from `requestIntent`.

**Evaluation context (trusted) — corrects `AS76-F001`.** A second, separately branded trusted argument, `evaluationContext`, carries exactly one field: `time` (the decision-relevant instant, as an explicit value — never read by `evaluate()` from the wall clock, an ambient `Date.now()`, or an unbranded caller-supplied field). Like `subjectContext`, `evaluationContext` is constructed only by a registered adapter wrapper's internal, trusted clock read, and carries the same brand mechanism — an arbitrary caller cannot hand `evaluate()` a backdated or forward-dated `time` to bypass expiry, because an unbranded `evaluationContext` fails structural/source validation exactly as an unbranded `subjectContext` does. Separating `evaluationContext` from `subjectContext` keeps "who" and "when" as independently testable trusted facts, even though both are ultimately produced by the same class of trusted wrapper.

**Request intent (untrusted).** `evaluate()`'s `requestIntent` argument is the caller's ordinary, untrusted statement of what it wants to do: `project`, `provider`, `action`, `resource` (the specific resource instance being acted on, already canonicalized by the adapter per §2/§9 and checked against a matching descriptor's `resource_scope` patterns), `environment`, `policy_version` (the exact version of the `policy` document argument below that the caller has pinned this attempt to — never "whatever is current," §6/§11), and an optional `contract_ref`/`task_id` (opaque references to an S3 Task Contract / S4 task record, for audit correlation only — never re-validated or re-interpreted by S5, per §10). `requestIntent` carries no time field of any kind — decision time comes exclusively from the trusted `evaluationContext`. Nothing in `requestIntent` is trusted merely because it was presented; only `subjectContext`'s and `evaluationContext`'s already-attested fields carry evaluative weight for who/what-credential/when questions.

**Evaluation.** `evaluate(subjectContext, requestIntent, policy, revocationList, evaluationContext)` is a pure function of exactly these five explicit arguments: the same five arguments always yield the same decision, with no hidden state, no network call, and — correcting `AS76-F001` — **no wall-clock read of any kind**; every decision-varying value, including the moment of evaluation, is now contained in the explicit inputs, so the earlier "injectable `now()`" framing (which was still external state relative to a four-argument pure function) is withdrawn. `policy` is the one immutable, version-identified document this specific attempt is pinned to (§6/§11) — `evaluate()` never resolves "the current policy" itself. `revocationList` is a separate, small, always-current, monotonic set of revoked `descriptor_id`s, supplied fresh by the caller on every call (§6) — its freshness is the caller's responsibility, not something `evaluate()` infers. Evaluation proceeds, in order: (a) `subjectContext`/`evaluationContext` brand and structural validation; (b) `requestIntent.policy_version` equality check against `policy`'s own version; (c) descriptor lookup by `(actor_role, project, provider, action, environment)`; (d) resource-scope match and precedence/tie resolution against the candidate descriptor(s) (§2); (e) expiry check against the matched descriptor using `evaluationContext.time`; (f) revocation-list membership check on the matched descriptor's `descriptor_id`; (g) credential-requirement check against `subjectContext`. The first failing step produces the decision; later steps are not evaluated once one has failed (short-circuit, not an aggregate score). **There is no consequence-tier evaluation step** — `consequence_tier` is a policy-authoring-time classification only (§8), never a per-request evaluation input, correcting `AS75-F002`.

**Decision.** A `CapabilityDecision` is exactly one of `ALLOW` or `DENY`, and is itself the complete, deterministic return value of `evaluate()` — it contains no field whose value could differ between two identical calls (see §12 for the separately-constructed, non-pure audit envelope this differs from, correcting `AS75-F005`; `evaluationContext.time` is the decision-time input, wholly distinct from the audit envelope's own `timestamp`, which records when a caller later wrapped the resulting decision). There is no third "warn but proceed" outcome — a request either has a technically matching, unexpired, unrevoked, credential-satisfied descriptor, or it does not. Every `DENY` carries a **stable denial-reason code from the one canonical vocabulary §4 defines** (corrects `AS76-F004` — this RFC states that vocabulary exactly once, in §4, and every other section references it rather than re-enumerating a differing subset). Every `ALLOW` carries the exact `descriptor_id` and `policy_version` it was granted under, so a later audit can trace precisely which policy artifact authorized the decision. Both outcomes carry the fixed, non-reword-able **non-authority disclaimer** (§5's text below) — mirroring S3's `authority_disclaimer` `const` field and S4's fixed non-authority statement — so an `ALLOW` can never be read, quoted, or logged without the caveat attached.

### 4. Default-deny handling and the canonical denial-reason vocabulary

**Corrects `AS76-F004`.** Earlier drafts stated a denial-reason vocabulary in §3 and then used a partially different set here in §4, leaving the implementation/schema/test enum ambiguous. **This section is the single canonical source of the denial-reason vocabulary; every other section (§3, §12, the design-decision table, Test plan, Implementation mapping) references it by name rather than re-enumerating any subset of it.**

Every axis fails closed on the unknown, not merely on the explicitly forbidden:

| Condition | Decision | Denial reason |
|---|---|---|
| `subjectContext` absent, structurally malformed, or missing a genuine brand from a registered adapter wrapper (§3, §9) | `DENY` | `UNTRUSTED_SUBJECT_CONTEXT` |
| `evaluationContext` absent, structurally malformed, or missing a genuine brand from a registered adapter wrapper (§3, §9) | `DENY` | `UNTRUSTED_EVALUATION_CONTEXT` |
| `actor_role` not a recognized role | `DENY` | `UNKNOWN_ACTOR_ROLE` |
| `provider` not a registered adapter | `DENY` | `UNKNOWN_PROVIDER` |
| `action` not declared by any descriptor for the resolved `(actor_role, project, provider, environment)` | `DENY` | `UNKNOWN_ACTION` |
| `project` not `*` and not matching any descriptor's `project` | `DENY` | `UNKNOWN_PROJECT` |
| `environment` not a registered value | `DENY` | `UNKNOWN_ENVIRONMENT` |
| `resource` was not already canonical per the originating adapter's own contract (§2, §9) | `DENY` | `MALFORMED_REQUEST` |
| `resource` is canonical but matches no descriptor's `resource_scope` pattern | `DENY` | `RESOURCE_SCOPE_MISMATCH` |
| `requestIntent.policy_version` does not exactly equal the presented `policy` document's own version | `DENY` | `POLICY_VERSION_MISMATCH` |
| two or more descriptors tie at the highest combined project/resource specificity rank (§2) — an ambiguous policy-authoring defect, regardless of whether their other fields happen to agree | `DENY` | `AMBIGUOUS_POLICY_MATCH` |
| matched descriptor has expired as of `evaluationContext.time` | `DENY` | `EXPIRED` |
| matched descriptor's `descriptor_id` appears in the presented `revocationList` | `DENY` | `REVOKED` |
| matched descriptor requires a credential class `subjectContext` does not attest as available, or attests a different class | `DENY` | `CREDENTIAL_REQUIREMENT_UNSATISFIED` |
| request is structurally malformed in any other way (missing required field, wrong type) | `DENY` | `MALFORMED_REQUEST` |

**The complete canonical enum, once:** `UNTRUSTED_SUBJECT_CONTEXT`, `UNTRUSTED_EVALUATION_CONTEXT`, `UNKNOWN_ACTOR_ROLE`, `UNKNOWN_PROVIDER`, `UNKNOWN_ACTION`, `UNKNOWN_PROJECT`, `UNKNOWN_ENVIRONMENT`, `RESOURCE_SCOPE_MISMATCH`, `POLICY_VERSION_MISMATCH`, `AMBIGUOUS_POLICY_MATCH`, `EXPIRED`, `REVOKED`, `CREDENTIAL_REQUIREMENT_UNSATISFIED`, `MALFORMED_REQUEST`. No other denial-reason code exists in this RFC.

There is no generic catch-all `ALLOW` path and no "permissive by default, deny-listed exceptions" mode. A capability exists only where a currently-valid, unexpired, matching descriptor explicitly says so. This is the same fail-closed posture S4 already applies to orphaned locks and structurally invalid records ("never a silent default to some assumed state") and S3 applies to malformed evidence declarations — S5 inherits, not reinvents, that discipline.

### 5. Separation of technical capability, governance authority, and human risk acceptance

Three independent questions, never conflated:

1. **May this happen?** — Governance authority. Decided by Paulo/Architect/RFC-Decision-ADR chain, described (not granted) by an S3 Task Contract's `authorization_references`. S5 never evaluates this question and never consumes a Task Contract's authorization fields to make its own decision.
2. **Can this happen?** — Technical capability. Decided exclusively by S5's `evaluate()` against the current policy. This is the only question S5 answers.
3. **Is this acceptable given the consequence?** — Human risk acceptance. Decided by Paulo (or Paulo-delegated policy) at the consequence tiers `§7` names, informed by, but never satisfied by, an `ALLOW` decision.

Every `CapabilityDecision`, `ALLOW` or `DENY`, carries the following fixed, schema-`const` **non-authority disclaimer**, worded to parallel S3's `authority_disclaimer` and S4's non-authority field exactly:

> This capability decision describes only what is technically permitted under the pinned policy version presented to it. It does not itself grant governance authority, certify that an action should happen, accept risk, or satisfy any merge, deployment, or production-write approval requirement (`CORE-001`, `CORE-002`, `CORE-008`). An `ALLOW` decision from a Governance-authorized actor is necessary but never sufficient for a sensitive operation (§8); a `DENY` decision blocks the action regardless of any governance authorization that may otherwise exist.

No instance may soften, omit, or reword this field, mirroring `ML-DEVOS-AS-038`'s `AS38-F002` finding on the S3 equivalent.

### 6. Least-privilege scoping, revocation, expiry, and policy-version pinning

**Corrects `AS75-F003`.** The original design left the "currently loaded active policy version" as an undefined, ambient concept that `evaluate()` implicitly consulted, while simultaneously requiring an in-flight attempt to stay pinned to one policy version — two requirements that cannot both hold once policy changes mid-attempt, with no defined mechanism for emergency revocation to still reach a pinned attempt. V1 resolves this with **two orthogonal mechanisms**, both passed to `evaluate()` as explicit arguments (§3) rather than resolved internally:

- **Least privilege by construction.** A descriptor's `resource_scope` must be a bounded pattern set, never `["*"]` by default — an unbounded scope is a deliberate, explicit authoring choice, not the schema's default shape (the schema's structural validator rejects a missing/empty `resource_scope`, exactly as S3's `allowed_paths` must be non-empty).
- **Policy-version pinning (stable, per-attempt).** Policy documents are immutable once published (§11); an attempt resolves and pins exactly one `policy_version` at the point it first evaluates capability, and presents that same `policy` document and `requestIntent.policy_version` on every subsequent check for that same attempt. A normal policy publish that supersedes a descriptor does **not** retroactively affect an already-pinned, still-unexpired, not-yet-revoked grant for an in-flight attempt — this is a deliberate stability guarantee, not an oversight.
- **Revocation list (live, never pinned).** Emergency revocation is modeled as a **separate, always-current, monotonically-appended set of revoked `descriptor_id`s** — the `revocationList` argument (§3) — that the caller must fetch fresh on every evaluation call, independent of whichever `policy_version` the attempt itself is pinned to. A matched descriptor whose `descriptor_id` appears in the presented `revocationList` is `DENY`/`REVOKED` (§4) **regardless of policy-version pinning** — this is precisely the mechanism by which an emergency revocation reaches a pinned attempt without silently invalidating the pin for every other, unrelated purpose. A descriptor also stops being grantable to a *new* attempt the moment a superseded policy version no longer contains it (an ordinary, non-emergency form of retirement); the revocation list exists specifically for the case that cannot wait for the next ordinary policy publish.
- **Expiry.** Evaluated against the trusted `evaluationContext.time` explicit argument (§3, §11 — corrects `AS76-F001`'s prior "injectable `now()`" framing, which was external state relative to the function's own purity claim), never cached and never read from an ambient wall clock. An expired descriptor decides exactly as an absent one would (`DENY` / `EXPIRED`), never silently treated as "still valid until someone notices."
- **Determinism.** Because `policy`, `revocationList`, and `evaluationContext` are all explicit arguments rather than results of an internal "what's current"/"what time is it" lookup, `evaluate()` remains a pure function of its five arguments (§3) even though they individually have different real-world freshness expectations (pinned vs. always-current vs. always-fresh-per-call) — purity is a property of the function's signature over its complete explicit inputs, not of how quickly its caller refreshes any one particular argument.

A `requestIntent.policy_version` that does not exactly equal the presented `policy` document's own version is a caller-side integration defect, not a "stale, please upgrade" signal to `evaluate()` — it is `DENY`/`POLICY_VERSION_MISMATCH` (§4), and the caller must re-resolve which `policy` document it actually intends to present rather than expecting `evaluate()` to reconcile the mismatch on its behalf.

### 7. Credential and secret-reference requirements

S5 policy documents and decision records **never contain a secret value**. A descriptor's `credential_requirement.credential_class` names only a *class* of credential (e.g. `github_pat_scoped`, `cloudflare_api_token`, `none`) that must be attested as available through a mechanism entirely outside this RFC's scope (an environment variable's presence, a secrets-manager binding, a CI secret context). Per §3's correction of `AS75-F001`, that attestation (`credential_class` / `credential_available: true/false`) is carried in the **trusted `subjectContext`**, produced by a registered adapter/host — never accepted as free-form, self-asserted `requestIntent` — and evaluation checks only whether the *declared* requirement is satisfied by that already-trusted attestation, never the credential's actual value, validity, or expiry. Validating that an attested credential is genuinely live, unexpired, and scoped correctly is explicitly **out of scope** for S5 V1 and named as a disclosed limitation (§"Non-goals"), analogous to how S3's evidence-presence gate checks *presence and class label*, never sufficiency or content.

### 8. Sensitive-operation gates

**Corrects `AS75-F002`.** The prior draft implied a per-request, evaluation-time `CONSEQUENCE_TIER_GATE_UNSATISFIED` denial — a gate with no defined technical input, which would either have silently modeled human risk-acceptance/governance-approval as a CAN-mechanism input (contradicting §5's central boundary) or left an unspecified technical prerequisite. **V1 removes any evaluation-time consequence-tier gate entirely.** `consequence_tier` (§2) is, and remains, **exclusively a policy-authoring/validation-time structural classification**, never an `evaluate()` input and never a step in the evaluation order (§3). No `CONSEQUENCE_TIER_GATE_UNSATISFIED` denial code exists in this RFC.

Building on `consequence_tier` (§2) and `CORE-019`/`CORE-020`/`CORE-021`'s already-active consequence-escalation policy, the following action classes are **named sensitive-operation categories** that a descriptor authoring a matching action must declare at `consequence_tier: "high"` or `"highest"`, never lower, as a structural rule the **policy validator enforces when a policy document is authored/loaded** — not something `evaluate()` re-checks per request:

- protected-branch/`main` merge;
- deployment/production-write actions;
- remote-resource mutation (D1/R2/Access/DNS-class actions, per `CORE-019`'s already-required scoping fields);
- credential/secret management actions (rotation, issuance, revocation);
- any explicitly-flagged destructive action (deletion, force-push, irreversible data mutation).

A descriptor for one of these categories declared at `consequence_tier: "low"`/`"medium"` is a structural policy-authoring defect the **validator** rejects outright at policy-load time — this prevents a policy author from silently under-classifying a high-consequence action to make it easier to grant, mirroring `CORE-020`'s binding rule that consequence-sensitive claims "must not close solely on Builder `ACTOR_REPORTED` evidence." An `ALLOW` decision matched against a `high`/`highest`-tier descriptor still carries the §5 non-authority disclaimer unweakened, and its `consequence_tier` value is included in the audit envelope (§12) purely as descriptive metadata about which policy artifact authorized it — the tier informs what evidence/audit expectations the *caller/Architect* should apply around the resulting action, never a decision `evaluate()` itself makes. Whether an actual human approval/risk-acceptance step is required for a `high`/`highest`-tier action remains entirely a Governance/Paulo concern (§5), outside `evaluate()`'s decision surface.

### 9. Provider adapter boundaries

An **adapter** is a bounded, explicitly registered translation layer between one provider's native vocabulary and this RFC's provider-neutral request/descriptor shape (§2–§3). V1 names exactly five adapter slots, matching `ML-DEVOS-ARCH-001` §4's own enumeration: `shell`, `github`, `cloudflare`, `mcp`, `browser`. A sixth, `future`, is reserved for a provider not yet named, added only by a future governed extension to the bounded provider-name vocabulary (never an ad hoc string).

An adapter's responsibility is strictly translation and **never** decision-making:
- it maps a provider-native action identifier (a GitHub REST endpoint, a shell command class, a Cloudflare API operation, an MCP tool name, a browser automation action) to this RFC's `(provider, action)` pair;
- it canonicalizes a provider-native resource identifier per its own contract (below), producing a `resource` value checkable against a descriptor's `resource_scope` patterns — an adapter that cannot canonicalize a given resource value must surface it as `MALFORMED_REQUEST`, never guess or pass it through partially normalized;
- it is the **sole public invocation surface** an external caller ever uses (§3, correcting `AS76-F002`) — an adapter exposes its own wrapper (e.g. `adapters.github.request(requestIntent)`), which internally derives `subjectContext`/`evaluationContext` from the adapter's own trusted execution environment and mints their brand, then calls the internal `evaluate()` core; `evaluate()`'s raw five-argument signature is never itself the surface an arbitrary caller reaches;
- it never itself decides `ALLOW`/`DENY` — every adapter-translated request still flows through the one `evaluate()` function (§3);
- it never embeds provider-specific authority semantics (e.g. "this GitHub token has admin scope, so allow everything") into the core model — a provider's own permission concepts are a capability-existence fact the adapter surfaces as an attested `credential_class`/`credential_available` pair (§7) inside the trusted `subjectContext`, never a decision shortcut.

**Per-adapter canonicalization contracts (corrects `AS76-F003`).** A single universal canonicalization recipe cannot serve five structurally different resource domains; each V1 adapter instead defines its own canonical resource shape and rejection rule, and the core matcher (§2, §3) treats whatever a given adapter emits as an opaque, already-canonical string it never re-decodes:

| Adapter | Canonical resource shape | Rejection rule (→ `MALFORMED_REQUEST`) |
|---|---|---|
| `shell` | An absolute filesystem path with traversal (`.`/`..`) and symlink components resolved by the adapter before comparison; platform path-separator normalized to `/`. | Any path the adapter cannot resolve to an absolute, traversal-free form (e.g. a dangling symlink, a path escaping an expected root) is rejected, never resolved partially. |
| `github` | The provider's own normalized `owner/repo` identifier, optionally suffixed `:<ref-or-path>` using GitHub's own ref/path syntax verbatim — no additional generic decoding applied on top of GitHub's own identifier rules. | An identifier that does not parse as a well-formed GitHub owner/repo(/ref/path) per GitHub's own rules is rejected. |
| `cloudflare` | The provider's own opaque zone/resource identifier, used byte-for-byte exactly as Cloudflare's API returns it — **no percent-decoding or normalization is applied**, since decoding an opaque ID can itself change its meaning. | An identifier the adapter did not itself obtain from a genuine Cloudflare API response/reference is rejected, never accepted as an arbitrary caller-supplied string. |
| `mcp` | The resource URI exactly as the MCP specification defines its own canonical form — no additional generic percent-decoding beyond what the MCP spec itself requires. | A URI that does not conform to the MCP spec's own resource-URI grammar is rejected. |
| `browser` | A canonical URL per the WHATWG URL Standard's own normalization (scheme, host, default port stripped, path, query — fragment excluded, since a fragment never reaches the server and is not a distinct resource for capability purposes). | A string that does not parse as a valid URL under the WHATWG algorithm is rejected. |

Wildcard matching (§2) always operates over the string form a given adapter contract emits above, never over a provider-native or partially-decoded form. This bounded table is not an exhaustive API catalog — it names each provider's canonicalization *category* and fail-closed rule precisely enough to make V1 matching deterministic and non-lossy; a future implementation elaborates the exact algorithm per adapter within these stated bounds.

An adapter's own trustworthiness — whether it correctly, honestly performs the attestations §3 and this section require of it — is itself a trust boundary this RFC discloses but does not close (see Threat model, below); a compromised or buggy adapter registered as a valid `attested_by` source remains a real residual risk for a future phase (S7/S9, or a separately governed capability-onboarding review under `CORE-008`) to address. The brand mechanism (§3) closes the *arbitrary-external-caller* forgery vector; it does not make every registered adapter individually trustworthy.

Adapter registration is a static, versioned list (mirroring the bounded `provider` enum in §2), not a runtime plugin-discovery mechanism — V1 explicitly excludes dynamic adapter loading as a future-phase concern, consistent with "smallest gateway that answers the CAN question."

### 10. Composition with S3 Typed Task Contracts and S4 Task State

S5 references, but never duplicates or re-validates, S3/S4 artifacts:

- A `CapabilityRequest` may carry an opaque `contract_ref`/`task_id` purely for audit correlation (§12) — S5 never re-opens, re-validates, or re-interprets the referenced Task Contract's `scope`/`claims`/`evidence` fields, nor the referenced task record's `state`/`owner`/`revision`. Those remain entirely S3's and S4's own concerns.
- S5 does not gate S4's `transition()` calls, `claim()` calls, or any other kernel operation directly — S4 remains, exactly as `ML-DEVOS-RFC-016` states, a library that "performs no general actor permission check... until S5 exists." A future, separately authorized integration RFC would decide whether/how a caller invokes `evaluate()` before calling into S4's kernel; this RFC does not itself wire that integration, since doing so would silently expand S4's already-accepted, closed interface.
- S3's `scope.remote_resources_involved`/`protected_main_or_deploy_in_scope`/`production_write_in_scope`/`credential_or_security_in_scope`/`destructive_actions_in_scope` boolean flags and S5's `consequence_tier`/sensitive-operation categories (§8) describe overlapping real-world concerns from two different documents' perspectives (a task's declared scope vs. a capability descriptor's technical classification) — this RFC does not merge them into one shared field, avoiding exactly the memory-boundary conflation `ML-DEVOS-ARCH-001` §11 warns against for Task Engine State vs. every other store. A future implementation may recommend keeping them consistent by convention, but S5 does not read or write S3's schema fields, and S3's schema is not modified by this RFC.

### 11. Idempotency, retry, concurrency, and policy-version implications

- **Read-only, side-effect-free evaluation.** `evaluate(subjectContext, requestIntent, policy, revocationList, evaluationContext)` is a pure read over its five explicit arguments — it has no persisted state of its own to corrupt, no lock to acquire, no idempotency-key ledger to maintain, and (correcting `AS76-F001`) no wall-clock read of any kind, unlike S4's mutating operations. A retried call with byte-identical arguments (including an unchanged `revocationList` snapshot and an unchanged `evaluationContext.time`) always returns the identical decision — idempotency is a structural property of the function's purity given its *complete* explicit inputs, not a separately implemented mechanism and not a claim that held only over four of the values the decision actually depends on. Purity does not require the caller to refresh `revocationList` slowly, or to construct a fresh `evaluationContext` only occasionally; it only requires that whatever value is actually passed for each argument be treated as part of the pure function's input, exactly like `policy`.
- **Policy versioning and attempt pinning.** Policy documents are immutable once published; a change to any descriptor produces a new `policy_version` rather than mutating an existing one in place. An attempt pins one resolved `policy_version` (and the exact `policy` document matching it) for its entire lifetime, per §6 — this mirrors S4's `revision` fencing philosophy (never mutate a committed record; the next state is a new version) applied to a configuration artifact instead of a task record, while §6's separate revocation list provides the emergency-override path a purely version-pinned model alone could not.
- **Concurrency.** Because evaluation has no shared mutable state, concurrent `evaluate()` calls require no lock, mutex, or serialization primitive of any kind — unlike S4's genuine need for a `wx`-exclusive lock file around its read-validate-mutate-persist cycle. This is a direct consequence of S5 V1 being a pure decision function rather than a stateful store.
- **Policy-version implications for a task/attempt.** A future integration should resolve and pin one `policy_version`/`policy` pair to a task/attempt at the point capability is first evaluated for it, present that same pinned pair on every subsequent capability check for that same attempt (§6), and always fetch `revocationList` fresh on each such check regardless of pinning. This RFC names the requirement; it does not implement the binding mechanism, which belongs to the future integration RFC named in §10.

### 12. Audit and evidence events

**Corrects `AS75-F005`.** The prior draft described `evaluate()` as pure while also saying it "produces" an audit event carrying `event_id`/`timestamp` — fields with no defined source, which would either make `evaluate()` itself impure (if generated internally) or leave the API incomplete (if merely assumed to exist externally). V1 resolves this by **strictly separating the pure decision from a separately-constructed audit envelope**, which is never itself part of `evaluate()`'s return value:

- **The `CapabilityDecision` (§3) is, and remains, fully pure** — `outcome` (`ALLOW`/`DENY`), matched `descriptor_id` or `denial_reason`, `policy_version`, and the non-authority disclaimer. Nothing in it varies between two calls presenting identical arguments.
- **A separate `AuditEnvelope` wraps a decision after the fact**, constructed by whichever caller/adapter chose to invoke `evaluate()` — never by `evaluate()` itself. Its minimum fields: `event_id` (assigned by the constructing caller — e.g. a fresh UUID it generates — never by `evaluate()`), `timestamp` (the constructing caller's own clock read at the moment it builds the envelope — a distinct concept from `evaluationContext.time`, §3/§11's trusted decision-time *input*; the envelope's `timestamp` records when the decision was later wrapped/logged, and is never a substitute for, or interchangeable with, the value `evaluate()` actually used for expiry math), the `subjectContext`/`requestIntent`/`evaluationContext` that were actually presented, the resulting `CapabilityDecision`, and an `evidence_provenance` field.
- **Provenance must be explicitly chosen by the constructing party based on its own actual observation, never defaulted or inferred merely because a decision exists.** A caller that itself invoked `evaluate()` and is reporting its own result labels the envelope `ACTOR_REPORTED`; a supervising process that independently observed the same call (e.g. a wrapping CI step) may label it more strongly, per the five `ML-DEVOS-ARCH-001` §6 classes — but nothing in this RFC infers a provenance class automatically, since provenance describes *how* evidence was produced and observed, not merely that a decision was returned.
- **This separation preserves both properties the prior draft conflated.** A retried call with identical arguments still returns a byte-identical `CapabilityDecision`, proving `evaluate()`'s purity; two different callers (or two retries) each wrapping that same decision in their own `AuditEnvelope` may legitimately produce two different `event_id`/`timestamp` pairs — this is expected and does not violate `evaluate()`'s purity, because envelope construction is explicitly not part of `evaluate()`.

**This RFC does not claim that S7 Evidence Store or S9 Evidence Gate already exist** — an `AuditEnvelope` is, in V1, an in-process value plus whatever the caller chooses to log; S5 does not itself provide durable, tamper-evident audit storage (that capability, if needed, is S7's and S11's concern). This bounded honesty mirrors S4's own disclosed limitation that its bounded transition history is not Run History and is not a substitute for a future dedicated store.

## Scope

This RFC proposes the S5 design only: capability-descriptor schema, decision/request/denial-reason contracts, default-deny rules, the technical-capability/governance-authority/risk-acceptance separation, least-privilege/revocation/expiry/stale-policy behavior, credential-requirement (not credential-value) handling, sensitive-operation gate classification, provider adapter boundaries, audit-event shape, composition with S3/S4, and idempotency/concurrency/policy-versioning implications, with an explicit comparison and V1 selection for each required design decision. It affects `Dillaab-source/maisog-labs` only (no other project is registered under Sentinel — `projects/registry.json` remains `EMPTY`).

## Non-goals

This RFC does **not**:

- write any executable implementation, schema file, or test file (`D-058`'s explicit authorization boundary — this cycle is proposal/audit only);
- create or mutate any live capability policy, credential, or secret;
- validate that an attested credential is genuinely live, unexpired, or correctly scoped (§7's disclosed V1 limitation — credential *value* validation is out of scope);
- implement S6 isolated execution, S7 evidence storage/QA execution, S8 orchestration/dispatch, S9 Evidence Gate acceptance logic, S10 CI/rulesets, S11 memory/observability, S12 project overlays, S13 release/runtime verification, or S14 the production pilot;
- change any `CORE-*` rule's meaning, any actor's authority, `manifest_version`, the Sentinel capability baseline version, or any ADR;
- wire S5 into S4's kernel operations or S3's contract validator — that integration, if pursued, is a future, separately authorized RFC (§10);
- implement dynamic adapter/plugin discovery, an externally hosted policy service, or any remote/cloud resource;
- authorize any later phase or itself constitute S5 implementation authorization.

## Affected rules

**No `CORE-*` rule is added, modified, or superseded by this RFC.** S5's design consumes `CORE-001`, `CORE-002`, `CORE-008`, `CORE-019`, `CORE-020`, and `CORE-021` exactly as currently written, and must validate any future implementation against them unchanged. No amendment to `ML-DEVOS-ARCH-001` is proposed by this RFC — the frozen §4/§5 Capability Registry/Gateway description already anticipates exactly this mechanism; S5 fulfills that reservation rather than amending it.

## Alternatives considered

### 1. Fold S5 into S4's kernel as an additional guard clause

Rejected. This would collapse two phases `ML-DEVOS-SIP-001`'s roadmap deliberately separates, and would force every future capability-policy change through S4's already-closed, Architect-accepted implementation surface, re-opening a phase that should remain stable.

### 2. Adopt an existing open-source policy-as-code engine (e.g. OPA/Rego, Casbin)

Rejected for V1, for the same reason `ML-DEVOS-RFC-016` rejected an external state-machine library: a general-purpose policy engine assumes a much larger surface (its own DSL, runtime, and often a live service) than a bounded provider-neutral descriptor/decision model needs. Revisiting this remains open if policy complexity later outgrows a static descriptor list — not rejected forever, rejected for this proposal's bounded scope.

### 3. Let each provider adapter make its own allow/deny decision locally

Rejected. This would scatter the CAN-decision logic across five-plus adapters with no single deterministic function to test, audit, or reason about, and would risk each adapter quietly inventing its own denial-reason vocabulary and default-deny discipline — exactly the inconsistency a single `evaluate()` function exists to prevent.

### 4. Pre-materialize a resolved permission matrix at policy-publish time instead of evaluating per request

Considered and rejected as the *primary* mechanism (§"Required design decisions" — revocation/expiry evaluation time) for the same reason S4 rejected age-based automatic lock recovery: a materialized snapshot can silently outlive the real descriptor's expiry/revocation, reintroducing exactly the kind of stale-authority gap `CORE-002` exists to prevent.

### 5. Allow a governance-authorized actor to bypass a missing capability descriptor as an emergency escape hatch

Rejected outright, not merely for V1. This is precisely the Capability≠Authority substitution `ML-DEVOS-ARCH-001` §5 forbids; an emergency path, if ever needed, belongs to a separately governed `WAIVER`-class change with its own explicit, time-boxed, Paulo-approved terms (`CHANGE_GOVERNANCE_POLICY.md` §1's `WAIVER` row) — never a silent S5 bypass mode.

## Risks

### Over-scoping into later phases
Mitigation: the explicit non-goals list and §10's composition boundary name exactly what S6/S7/S8/S9 remain solely responsible for; any future implementation review should re-check the diff against this list.

### S5 becomes a de facto governance-authority decider
Mitigation: §5's fixed non-authority disclaimer and the explicit "capability exists, governance authority absent" design decision keep S5 answering only the CAN question; any future caller conflating an `ALLOW` decision with authorization is a caller-side defect this RFC's disclaimer is designed to make visible, not an S5 design gap.

### Credential-requirement checking creates a false sense of security
Mitigation: §7 explicitly discloses that credential *value*/liveness validation is out of scope for V1; a future phase must not cite S5's `credential_available` attestation as proof a credential is actually valid.

### A policy-version mismatch blocks legitimate work during a policy rollout
Mitigation: this is a deliberate, disclosed availability trade-off, exactly like S4's orphaned-lock fail-closed choice — a caller presenting a `requestIntent.policy_version` that does not match its own presented `policy` document is `DENY`/`POLICY_VERSION_MISMATCH` (§6) rather than being silently reconciled, trading a small operational friction for the guarantee that no attempt evaluates against policy it never actually observed.

### Ambiguous policy authoring produces contradictory descriptors
Mitigation: `AMBIGUOUS_POLICY_MATCH` (§2, §4) fails closed on any specificity tie — regardless of whether the tied descriptors' `consequence_tier`/`credential_requirement` happen to agree — rather than picking one match arbitrarily; this pushes the defect back to policy authoring/review rather than silently resolving it inside the evaluator.

### A pinned attempt outlives an emergency revocation, or a revocation list is stale/omitted
Mitigation: §6's two-mechanism design exists specifically to prevent the first outcome — revocation is checked live on every call regardless of policy-version pinning. The second remains a disclosed residual risk: a caller that fails to fetch a fresh `revocationList` (or omits it) receives a decision that cannot reflect a revocation it never presented; this is a caller-side integration responsibility this RFC states explicitly (§6, §11) rather than a gap `evaluate()` itself can silently detect.

### Provider adapter boundary proves too rigid for a future provider's native model
Mitigation: §9's bounded provider enum is explicitly extensible only through a future governed change, not a runtime mechanism — disclosed as a deliberate V1 scope bound rather than a discovered gap later.

## Migration impact

None. No live capability policy, credential requirement, or decision record exists to migrate (nothing has ever technically enforced a capability decision in this repository). No existing file, schema, or record is modified by this RFC.

## Security / trust impact

This RFC proposes the mechanism that would, once implemented, technically enforce `CORE-002`/`CORE-008` for the first time — a genuine trust-boundary-relevant change, though this RFC itself creates no new trust boundary and grants no new capability. `TRUST_BOUNDARIES.md` TB-7 ("a tool, credential, or API access granted to any actor or mechanism is a capability fact, not an authorization fact") is the exact invariant S5 is designed to make technically checkable rather than merely stated. The gateway introduces no new credential, secret, or remote-resource access of its own (`CORE-008`, `CORE-019` both inapplicable to this proposal — no remote/cloud action is proposed); a future implementation's own security review must independently confirm the evaluator never logs, stores, or exposes an actual secret value, only the class-level attestations §7 describes.

## Evidence requirements

A future S5 implementation's acceptance should require, at minimum:

- `INDEPENDENTLY_INSPECTED` review of the descriptor schema/decision-function/adapter-boundary source against this RFC's design;
- Builder-reported (`ACTOR_REPORTED`) focused test execution covering, at minimum, every default-deny condition and its exact denial reason from §4's single canonical vocabulary; expiry/pinning/revocation-list-override behavior (§6); the resource-matching precedence and ambiguous-match cases per each adapter's own canonicalization contract (§2, §4, §9); the trusted `subjectContext`/`evaluationContext` brand boundary and the adapter-wrapper-only invocation path (§3, §9); the pure-decision/audit-envelope separation including the distinctness of `evaluationContext.time` from the envelope's `timestamp` (§12); and non-authority-disclaimer presence on every decision;
- independent inspection that no descriptor, `subjectContext`, `evaluationContext`, decision, or audit envelope ever contains a literal secret value, only class-level credential attestations (§7);
- independent inspection that the sensitive-operation consequence-tier structural rule is enforced only at policy-validation time, never as a per-request evaluation gate (§8);
- independent inspection that `evaluate()` never generates `event_id`/`timestamp` internally, never reads an ambient wall clock, and that identical calls with identical arguments (including an identical `evaluationContext`) return byte-identical `CapabilityDecision`s (§3, §11, §12);
- independent inspection that `evaluate()`'s raw signature is not itself exposed as the public caller-facing API in the reference implementation, and that an unbranded `subjectContext`/`evaluationContext` is mechanically rejected rather than merely discouraged by convention (§3, §9);
- explicit confirmation that S4's kernel interface and S3's contract schema remain byte-identical (no accidental widening of an already-closed phase's surface).

## Threat model and trust boundaries

- **Threat: a caller presents a `requestIntent.policy_version` that does not match its own presented `policy` document, to evade a revocation.** Mitigated by §6's strict equality check between `requestIntent.policy_version` and the presented `policy`'s own version — any mismatch is `DENY`/`POLICY_VERSION_MISMATCH`, never silently resolved to "whatever is current" or "whatever the descriptor's own version says" (there is no such ambient "current" for `evaluate()` to consult, per `AS75-F003`'s correction).
- **Threat: a caller omits or presents a stale `revocationList` to keep using an already-revoked descriptor.** Disclosed, not eliminated (§"Risks") — `evaluate()` can only check the `revocationList` it is actually given; a caller that fails to fetch the current list receives a decision that cannot reflect a revocation it never presented. This is a caller-side integration responsibility this RFC states explicitly (§6, §11), analogous to how a certificate-revocation check is only as good as the CRL/OCSP freshness the checking party actually fetches.
- **Threat: a compromised or misconfigured adapter reports a false `credential_available: true`, or falsely attests an `actor_role` it is not entitled to assert.** Corrected in part by `AS75-F001`/`AS76-F002`'s remediation — a `subjectContext`/`evaluationContext` is only accepted when it carries a genuine brand minted by a registered adapter wrapper's internal construction path (§3, §9), which closes the *caller-side* forgery vector (an arbitrary external caller can no longer construct a matching object literal at all, since it lacks the means to mint the brand). It does **not** close the *adapter-side* trust boundary: S5 cannot itself detect a registered adapter that lies about the content it attests. Named as a disclosed V1 limitation (§3, §9, §"Risks") — a future phase (S7/S9, or the adapter's own separately governed capability-onboarding review, `CORE-008`) must address adapter trustworthiness itself.
- **Threat: a caller supplies a backdated or forward-dated evaluation time to bypass expiry.** Closed by `AS76-F001`'s remediation — `evaluationContext.time` is a trusted, branded value only a registered adapter wrapper's own clock read can produce (§3); an untrusted `requestIntent` carries no time field at all, so there is no caller-controlled timestamp path into the expiry check.
- **Threat: genuine end-user/process identity is never authenticated, only relayed by an adapter.** Out of scope for S5 V1 by explicit design (§3, §9) — `evaluate()` trusts a `subjectContext` exactly to the extent its constructing adapter wrapper is itself trustworthy; S5 specifies the *shape* a trusted assertion must take and mechanically requires it come from a genuinely branded, registered-adapter-constructed source, but does not itself implement identity/authentication verification. This mirrors `ML-DEVOS-RFC-016`'s identical disclosed limitation for S4's bare `actor_id`.
- **Threat: a policy-authoring mistake grants an overly broad `resource_scope`.** Mitigated structurally (§2, §6 — non-empty, explicit, bounded-grammar scope required, with deterministic precedence, over each adapter's own canonical resource form) but not eliminated; a future implementation's test plan (§"Test plan") must include negative fixtures proving an overly broad pattern is still bounded to what it literally matches, not silently widened.
- **Trust boundary carried forward from `TRUST_BOUNDARIES.md` TB-7:** this RFC's entire purpose is to make TB-7's already-stated principle technically checkable; it does not itself resolve TB-7, since TB-7 is a statement about the *current, actual* state of the repository that remains true (capability without authority) until a real implementation exists and is wired into an actual enforcement point.

## Misuse cases

- A caller invokes `evaluate()`, receives `DENY`, and proceeds anyway because S5 is advisory-only in the absence of a real enforcement wrapper. Mitigated by disclosure only at this design stage — the "is not an active enforcement daemon" boundary (§1) means a future implementation/integration RFC must explicitly wire the adapter wrapper's decision to actually block the call site, or S5 remains theater. This RFC names that dependency rather than hiding it.
- A caller attempts to construct its own `subjectContext`/`evaluationContext` object literal and pass it directly to `evaluate()`, bypassing an adapter wrapper entirely. Mitigated per `AS76-F002` — `evaluate()` mechanically rejects a value lacking a genuine brand (`UNTRUSTED_SUBJECT_CONTEXT`/`UNTRUSTED_EVALUATION_CONTEXT`, §4), which a hand-constructed object literal cannot carry. This does not, by itself, prevent a *registered* adapter's own wrapper from being colluding or careless (§9's disclosed residual risk) — the brand boundary closes external forgery, not internal adapter misbehavior.
- A caller quotes an `ALLOW` decision, minus its non-authority disclaimer, as proof that an action was authorized. Mitigated by the disclaimer being schema-`const`/non-removable (§5), exactly as S3's `authority_disclaimer` already is.
- A policy author sets `consequence_tier: "low"` on a sensitive-operation-category action to make it easier to grant. Mitigated structurally by §8's policy-validation-time rule rejecting under-classified sensitive actions before the policy document is ever loaded.
- A caller reuses a stale `revocationList` snapshot indefinitely to keep an already-revoked descriptor usable. Disclosed, not eliminated (§"Risks", §"Threat model") — freshness of `revocationList` is a caller-side integration responsibility this RFC states explicitly rather than something `evaluate()` can enforce on an argument it did not fetch itself.

## Failure modes

- **Policy document fails to load/parse.** Fails closed: no descriptor is available, so every request presenting that policy version is effectively `POLICY_VERSION_MISMATCH`/`DENY` against any other loadable document, and outright unusable as a `policy` argument itself. No fallback to a cached or default-permissive policy.
- **`revocationList` fails to load/parse or is unavailable.** Fails closed: the caller must not substitute an empty list to "unblock" evaluation when the real list could not be fetched — a future implementation must treat an unavailable revocation source as its own distinct error, never as "no revocations exist."
- **An adapter wrapper's trusted clock read fails or is unavailable.** Fails closed: the wrapper must not fall back to constructing an `evaluationContext` with a placeholder or default time — no branded `evaluationContext` is produced, and the request cannot proceed to `evaluate()` at all, rather than proceeding with a fabricated time value.
- **A registered adapter's canonicalization contract (§9) cannot resolve a given resource.** Fails closed at the adapter boundary: `MALFORMED_REQUEST`, never a partially-normalized value passed through to the core matcher.
- **Structurally malformed descriptor in an otherwise loadable policy document.** The policy loader/validator must reject the entire policy version as invalid at load time (fail closed on the whole document), never silently skip one bad descriptor and proceed with a partially-valid policy — mirroring S4's structural validation running at both load and pre-persistence boundaries.

## Test plan

A future implementation's focused test suite must cover, at minimum: every default-deny condition with a distinct fixture per denial-reason code from §4's single canonical vocabulary, including `UNTRUSTED_SUBJECT_CONTEXT`/`UNTRUSTED_EVALUATION_CONTEXT` for a missing/malformed/unbranded trusted argument, and a hand-constructed object literal (not produced by any adapter wrapper) proving it is mechanically rejected rather than merely discouraged by convention; expiry evaluated at exactly the `evaluationContext.time` boundary instant (equal-to and one-tick-past), and a fixture proving `requestIntent` cannot carry any time-bearing field that influences the expiry check; a `requestIntent.policy_version` mismatched against the presented `policy`'s own version; a matched descriptor whose `descriptor_id` appears in `revocationList` even under a still-validly-pinned older `policy_version` (proving the emergency-override path); the ambiguous-policy-match case with two descriptors tied at the same specificity rank, including a tie where their `consequence_tier`/`credential_requirement` happen to agree (must still `DENY`); resource-matching precedence per each of the five adapters' own canonicalization contracts (§9) — including at least one traversal/symlink case for `shell`, one malformed-owner/repo case for `github`, a byte-for-byte opaque-ID case for `cloudflare` proving no decoding is applied, an MCP-spec-conformance case, and a WHATWG-URL-normalization case for `browser` — each resolving deterministically or `MALFORMED_REQUEST`, never guessed; a sensitive-operation-category descriptor declared at a too-low `consequence_tier` (must fail policy validation at load time, never at evaluation); credential-requirement satisfied vs. unsatisfied vs. wrong-class via `subjectContext`; a retried identical `evaluate()` call (including an identical `evaluationContext`) returning a byte-identical `CapabilityDecision` while two separately-constructed `AuditEnvelope`s around that same decision carry different `event_id`/`timestamp`, and a fixture proving `evaluationContext.time` and the envelope's `timestamp` are independent values that may legitimately differ; and a positive-path `ALLOW` carrying the exact `descriptor_id`, `policy_version`, and unweakened non-authority disclaimer. Concurrency tests are not required for V1's pure-function evaluator (§11), unlike S4's genuine need for real-process lock tests.

## Implementation mapping

Not authorized by this RFC. A future implementation cycle would, at minimum, produce: `devos/capabilities/capability-descriptor.schema.json`, `devos/capabilities/subject-context.schema.json`, `devos/capabilities/evaluation-context.schema.json`, and `devos/capabilities/decision.schema.json` (structural schemas; the trusted `subjectContext`/`evaluationContext` shapes kept structurally distinct from the untrusted `requestIntent` shape per §3, with their brand mechanism defined here rather than left to implementation improvisation); `devos/capabilities/validate-capability-policy.mjs` (structural + the §8 sensitive-operation-tier semantic rule, evaluated only at policy-load time, zero third-party dependencies, following S3/S4's precedent); `devos/capabilities/evaluate.mjs` (the pure, five-argument decision function per §3, exporting only the internal core — never the public caller-facing surface); `devos/capabilities/adapters/` (the five V1 adapter modules, each implementing translation, its own canonicalization contract per §9's table, and the sole public wrapper that constructs and brands `subjectContext`/`evaluationContext`); bounded valid/invalid example policy fixtures (including resource-matching precedence, revocation-list-override, and unbranded-context-rejection fixtures); and focused tests per the plan above. None of these files are created by this RFC.

## Unresolved questions

1. **Is the bounded V1 resource grammar (§2 — exact literal, single-trailing-`/*` prefix wildcard, or bare `*`) expressive enough for every V1 provider**, particularly ones whose resources are not naturally path-shaped (e.g. a Cloudflare zone/record, an MCP tool's own parameter space)? §2 now fully specifies the grammar and its matching precedence (correcting `AS75-F004`), but whether a future provider adapter can faithfully canonicalize its own resource identifiers into this exact-literal/prefix-wildcard grammar without lossy approximation remains something a future implementation's adapter design must demonstrate case by case, subject to Architect review.
2. **What is the concrete point that actually invokes a given adapter's public wrapper before a real tool call** — a future S8 Orchestrator responsibility, or a caller-side convention every actor is expected to follow? §3/§9 now settle *which* boundary constructs a trusted `subjectContext`/`evaluationContext` (the adapter wrapper, correcting `AS76-F002`), but not *what upstream mechanism decides when to call that wrapper* for a given real-world action. This RFC deliberately does not decide this (§10), naming it as a future, separately authorized integration RFC's job.
3. **How strong must the `subjectContext`/`evaluationContext` brand mechanism actually be** — a simple module-private token/class only adapter-internal code can construct, or a stronger cryptographic attestation (e.g. a signed handle)? §3/§9 state that no cryptographic system is required for V1 provided the trust assumptions and bypass limits are explicit, but a future implementation must choose and justify one concrete mechanism, subject to Architect review of whether the chosen strength is adequate for the process-isolation model the implementation actually runs under.
4. **Should a `DENY` decision itself be evidence-worthy** (i.e., should a denied attempt automatically produce a durable, tamper-evident audit record even before S7 exists), or is an in-process `AuditEnvelope` sufficient until S7/S11 exist? This RFC's §12 takes the minimal position (in-process envelope, `ACTOR_REPORTED`-or-stronger per the constructing party's own actual observation, never inferred) but flags this as an open question the Architect may want to revisit given `CORE-020`'s consequence-escalation direction.
5. **Who is responsible for keeping `revocationList` genuinely fresh in a real deployment** — a required minimum refresh interval, a push-based invalidation mechanism, or purely caller discipline with no enforced freshness bound? §6/§11 name the requirement that `revocationList` be fetched fresh per call, but this RFC does not specify a mechanism or a maximum acceptable staleness, leaving it to a future implementation/integration RFC.
6. **Does a future multi-project Sentinel deployment (`projects/registry.json` no longer `EMPTY`) require `project`-scoped policy isolation stronger than a single shared descriptor list filtered by the `project` field**, or does the single-list-with-a-project-field model (mirroring S3's `project` field) remain sufficient? Left open since no second project exists yet to motivate a concrete answer.
