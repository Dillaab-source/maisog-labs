======================================================================
1. OBJECTIVE
======================================================================

Rebuild the MaisogLabs website around one principle:

PUBLIC WEBSITE = presentation shell
ADMIN PORTAL = control center for content, layout, visuals, projects, journal,
branding, and approved design settings.

The public website should stay visually clean and lightweight. It should render
the MaisogLabs background/visual system and published content managed through
/admin.

The admin portal should become the place where Paulo manages the website
without editing source code.

Do NOT rewrite the entire site blindly.
Do NOT destroy existing content.
Do NOT assume old plans are implemented unless repository evidence proves it.

======================================================================
2. TARGET PRODUCT MODEL
======================================================================

        ADMIN PORTAL
             |
             v
   structured content/design data
             |
             v
     storage + media layer
             |
             v
       PUBLIC WEBSITE

The public website is not the primary editing surface.

The admin portal should eventually manage:
- Homepage/hero/about content
- Projects
- Journal entries
- Images/media/background assets
- Section visibility and order
- Navigation labels
- CTA/contact/social links
- Brand/logo assets
- Approved theme settings
- Typography from an allowed set
- Spacing/layout presets
- Card presentation presets
- Animation/reduced-motion settings
- Draft/published state
- Featured content
- Future portfolio items

The admin portal must NOT execute arbitrary code from user-entered content.
"Edit the design" means controlling safe design primitives and reusable
components, not raw production JavaScript/HTML/CSS.

======================================================================
3. DESIGN PHILOSOPHY
======================================================================

The public site should remain intentionally minimal:
- MaisogLabs cosmic/signature background remains the visual foundation.
- Content floats as premium interactive layers above it.
- Sections are modular, not permanently hard-coded.
- Cards may support horizontal/swipe behavior on mobile.
- Projects and Journal are dynamically managed.
- New content can be added from /admin without code changes.
- The site remains fast, responsive, and visually consistent.

Public site = renderer.
Admin portal = website control system.

8. CORE GOVERNANCE RULES
======================================================================

EVIDENCE STANDARD
Claims such as implemented, fixed, tested, secure, deployed, complete, or
working require verifiable evidence such as code, diff, tests, build output,
runtime output, HTTP response, deployment logs, screenshots, schema validation,
database records, or Cloudflare deployment evidence.

NO SELF-CERTIFICATION
Implementation completion is not independent verification.

CHANGE-SCOPED REVIEW
READY TO COMMIT: YES means no unresolved blocker introduced by, materially
affecting, or required for the specific change under review remains unresolved.
It does NOT mean the whole project has zero unresolved risk.

Broader modes:
- STAGE GATE REVIEW
- RELEASE REVIEW
- SECURITY REVIEW

20. IMPLEMENTATION PHASES
======================================================================

PHASE 0 — REPOSITORY RECONNAISSANCE
No functional changes. Inspect/report architecture, Git state, deployment,
content model, Projects, Journal, admin, auth, tests, storage, media, security,
and production assumptions. Stop and report reality.

PHASE 1 — GOVERNANCE BOOTSTRAP
Create/merge CLAUDE.md and brain/* governance files. Update AGENTS.md only as
needed. No public-site redesign yet.

PHASE 2 — GOVERNANCE BASELINE
Record baseline SHA, current architecture/capabilities/gaps/risks, governance
boundary. Create a clean governance commit.

PHASE 3 — GOVERNANCE SELF-REVIEW
Check contradictions, circular approval, impossible requirements, unnecessary
bureaucracy, ambiguous authority, and website-specific rules presented as
universal. Prepare Architect Sync handoff. STOP for independent review before
major functional implementation.

PHASE 4 — ADMIN ARCHITECTURE DESIGN
Design against repository reality. Expected target if compatible:
Public Next.js site -> read-only published content -> Cloudflare Worker API ->
D1 + R2 + auth/authorization + audit logging.
Document architecture before implementing.

PHASE 5 — CONTENT MODEL
Define schemas for site settings, navigation, sections, projects, journal,
media, theme settings, and publish state. Include migration strategy.

PHASE 6 — ADMIN AUTHENTICATION
Implement secure /admin access. Do not proceed with write features until
unauthorized access is proven blocked.

PHASE 7 — ADMIN CONTENT MANAGEMENT
Implement Projects CRUD, Journal CRUD, site content editing, publish/unpublish,
media selection/upload, section visibility/order.

PHASE 8 — ADMIN DESIGN CONTROLS
Implement safe controls for background/media, card preset, spacing, section
order, typography, theme tokens, animations, project rail, and journal behavior.
No arbitrary code execution.

PHASE 9 — PUBLIC WEBSITE DATA INTEGRATION
Refactor public site into a renderer of structured published data. Preserve the
MaisogLabs background and visual identity. Minimize hard-coded content.

PHASE 10 — JOURNAL
Add Journal as first-class managed content. It should be mobile-friendly,
support images/drafts/publishing, allow swipe/horizontal presentation where
appropriate, and be entirely admin-managed. Missing optional media must not
break the section.

PHASE 11 — MIGRATION
Migrate current site/project content safely. Verify counts/content before
deprecating old static paths. Do not destroy old data until verified.

PHASE 12 — VALIDATION
Run unit/schema/auth/admin mutation/public rendering/mobile/build/regression
checks and deployment dry-run where practical.

PHASE 13 — ARCHITECT SYNC
Provide change scope, diff, requirements, risks, tests, evidence, gaps, and
proposed commits.

PHASE 14 — COMMIT / DEPLOY
Only after approved review: commit, deploy, independently verify production,
and record production evidence.
